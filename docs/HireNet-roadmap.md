# HireNet 路线图：整体节奏

> 这份文档只回答一件事：**整个项目的节奏是什么样的**——每个阶段要达成什么、为什么是这个顺序、现在走到哪。
> 它不是 spec。每个阶段真正开工时，再单独写该阶段的 spec 和单元拆分（像 Phase 1 那样）。

---

## 一句话看懂节奏的逻辑

> **先把模型做对，再在模型上加能力。不在会变的地基上盖楼。**

整条线是一层一层往上垒的，每一层是上一层的地基：

```
工程地基  →  证明闭环  →  让闭环能安全承载真实价值  →  让真实价值流动、网络打开  →  网络自我增强
 Phase 0      Phase 1            Phase 2                      Phase 3                   Phase 4
  ✅           ✅              ← 现在                        (被 P2 红线挡着)         (被 P3 挡着)
```

- **记账要先于身份**：先有"谁该拿多少"，才谈"谁是谁"。
- **身份要先于结算**：没鉴权的身份不能打真钱。
- **结算要先于网络**：钱能动、能验证，市场才立得住。

每一层没做完，强行上下一层都会返工——这是这份路线图里反复出现的唯一一条铁律。

---

## 贯穿所有阶段的不变量（项目宪法级，不随阶段变）

无论走到哪个 Phase，下面这些都不松动：

- **钱**：整数基点贯穿 schema / DB / 代码，零浮点；余数显式分配；分账对账（各方之和 == charge）；**绝不跨 (currency, chain) 相加**。
- **身份**：creator / payee / caller 一律**服务端派生，绝不客户端可控**。这是"把钱付给对的人"的根。
- **账本**：`ledger` 始终是 **settlement-ready 但 settlement-decoupled**——记的是 amount + currency + chain 三元组、一 payee 一行、状态 `accrued`；钱怎么动是另一层的事。
- **节奏**：一个 Phase 一个命题，范围收紧，其余明确推后。警惕"换个标签把下一阶段的活塞进来"的范围蔓延。
- **审查**：money / auth / provenance 代码 = TIER-1，人逐行审，不例外；安全关键项加 Codex 跨模型二审。
- **测试**：断言真实行为/真实数据，不断言代理指标；**绝不写一个把 bug 固化下来的测试**；只 stub 外部边界（LLM）。
- **缺口**：已知没做的，必须是**显式 TODO / backlog**，不是悄悄缺失。

## Phase 0 — 工程化地基 ✅ 已完成

**命题**：把项目从"能演示的脚本堆"变成"可维护、可测试的工程"。

清掉了 `files/files/` 双层结构和被 track 的 `__pycache__`，整理成 `app/{routes,agents,schemas,services,templates,storage}`，建了 pytest + smoke 测试 + `.gitignore`。先铺测试网，再动文件。

**收口标志**：结构清晰、零行为改变、测试网就位。

## Phase 1 — 证明核心闭环 ✅ 已完成

**命题**：证明这个产品的核心价值闭环真的能跑——**注册一个知识资产 → 它被任务调用 → 版税自动回流到创作者 → 创作者看得见**。

**做到的闭环**：注册 1 个 SkillAsset（creator = 服务端身份的你）→ 触发 1 次用到它的任务 → `royalty_ledger` 出现一条 amount / currency / creator_id / status='accrued' 全对的 creator 行 → 收益页能显示。全程真实 SQLite 数据。

**这个阶段刻意守的边界（重要——这些是 Phase 2/3 的活）**：

- 离线、`ledger_only`、`accrued`——**钱不动**。
- 分账只有 creator / platform **两方**，platform 份额进 `agent_runs.royalty_splits` JSON、不占 ledger 行。
- **单 asset**（一次调用只用一个资产）。
- 身份是服务端 **stub**（`PHASE1_CREATOR_ID` 等），不是真鉴权。

**收口标志**：上面那条硬判据成立 + 全套测试绿 + 手动验收八步过 + Codex 全 Phase 跨单元审计 PASS。

## Phase 2 — 把已证明的闭环升级成"能安全承载真实价值" ← 现在

**命题**：Phase 1 证明了闭环*成立*，Phase 2 让它*可信*。收掉三条红线，让这条闭环具备承载真实价值的资格——**但本阶段仍然不动真钱**，做的还是记账层和身份层。

### 三条红线

**① 多方分账（头炮）**
- *是什么*：把"creator / platform 两方"推广成"一组 payee 各自一份额"。
- *为什么打头*：它最有设计基础（方案已归档在 `docs/phase-2-revenue-split.md`），而且它不只是红线，还**推进产品命题本身**——从"一个创作者拿钱"变成"整个贡献者网络都被署名、被分账"，这才是"知识资产归属层"真正的样子。
- *范围*：列表式 shares `[{payee, bps}]`；`resolve_split` 做成纯函数（唯一收口点）；结算时**冻结快照**（存 `applied_split`，保证可重放）；`royalty_ledger` 从"creator 一行"推广成"一 payee 一行"（`creator_id` → `payee_id` + `party` 列）；`platform_default` + 单资产可覆盖；舍入策略用枚举（如 `platform_absorbs`）。
- *仍然不做*：钱不动；不接任何支付框架/钱包。它只产出干净的"N 个 payee、各欠 X、在链 Y 上"的账本行。

**② 结算幂等**
- *是什么*：同一笔可计费/可结算事件不能被重复记账。
- *为什么*：现在按调用记账、无幂等键，一次重试就重复计费——这是接真钱前的红线。
- *范围*：设计好"什么算同一个事件"的幂等键；让记账/结算对重试天然安全。
- *注意*：一旦进入结算（钱真动），它从"backlog"升级为"前置"。见下面的黑客松轨。

**③ 真实鉴权**
- *是什么*：把服务端 stub 身份换成真实身份——创作者只看到自己的收益、注册需要身份。
- *为什么*：真实用户、真实钱之前，身份必须是真的。它同时关掉 tampered-asset 和 IDOR-stub 那两个已知缺口。
- *范围警告*：auth 极易膨胀成"做一整套用户系统"。**压到"最小真实身份"**那个程度即可；如果还是太大，它可以单独成一个 phase（Phase 2.5）。

### 依赖与顺序

- 多方分账（①）独立，先做，且直接服务黑客松。
- 结算幂等（②）在"钱要动"时立刻变成硬前置。
- 鉴权（③）放最后/或独立，因为它最容易膨胀，且不阻塞 ① 的记账逻辑。

### 收口标志

三条红线各自有 spec、测试、人审（TIER-1）+ 安全项 Codex 二审；闭环在"多方 + 幂等 + 真实身份"下仍然成立、对账仍然平。

## 黑客松轨（Cobo）— 贴在 Phase 2 之上的一条演示分支

> 这不是一个新 Phase，是一条**有边界的演示分支**，用来把 Phase 3 的"结算缝"提前证明给赞助方看。

**怎么插进来**：

1. **多方分账（Phase 2 ①，纯记账）** 产出"N 个 payee、各欠 X USDC、在链 Y"的账本行——这本来就是 demo 的地基（要演示"贡献者网络都拿到钱"，得先有多 payee 记账）。
2. **Cobo 结算适配器（Phase 3 的前切片）**：读 `accrued` 的 payee 行 → 调 Cobo Agentic Wallet 把 USDC（**测试网**）打给每个 payee → 翻成 `settled`。

**边界（必须守住）**：

- 适配器**独立成一层**、厂商无关、可替换；**不织进记账逻辑**，产品本体保持支付无关。
- 适配器**自带结算幂等**：每条账本行只结算一次、打款与翻 `settled` 原子完成。（钱一动，幂等就不可省——这是把红线 ② 的一个聚焦切片提前做掉。）
- 钱包模型用 Cobo 的"**Pact**"：owner 给 agent 一个受限授权（花费上限 + 允许收款方 + 有效期），agent **不持私钥**。这正是防"被劫持 agent 掏空钱"的机制。

**对 demo 收窄、真产品前补全**：泛化幂等和完整 auth 对"时间盒 + 单 owner + 测试网"的 demo 可以收窄；变成真用户、真钱的产品前要补回来。

## Phase 3 — 真实价值流动 + 网络打开

> 被 Phase 2 三条红线挡着。红线没收完，这一层立不住。

**命题**：让闭环里的"价值"从账面变成真实流动，并把网络从"自己的 9 个内部 Agent"打开成"外部也能参与的市场"。

### A. 真实机器支付（结算层）

- *是什么*：把 `accrued` 推进到 `settled`——钱真的从一个钱包到另一个钱包，走稳定币（USDC）/ x402 / AP2 / Cobo 之类的机器支付协议。
- *为什么被挡*：没有**结算幂等**会重复打真钱；没有**真实鉴权**不能给一个未验证的身份打钱。所以它压在红线 ②③ 之上。
- *接法*：账本当初就是 settlement-ready 的，所以这是在 ledger 之上贴一个结算适配器（黑客松轨已经先趟过一遍）。

### B. Agent 市场

- *是什么*：把 Agent 世界页从"叙事展示"变成真实资产市场——外部 agent/资产能注册、AgentCard（价格 + 成功率 + 创作者）、reputation 系统。
- *为什么被挡*：要知道"**谁**在注册、**谁**该拿钱"需要**真实鉴权**（红线 ③）；要给多个外部贡献者分账需要**多方分账**（红线 ①）。所以它压在 ①③ 之上。

**收口标志（方向性）**：一笔真实（哪怕测试网）的"任务 → 多方贡献者各自收到 USDC"端到端跑通；外部 agent 能注册并被调用、被记账。

---

## Phase 4 — 网络飞轮

> 被 Phase 3 挡着。这一层是"产品成为一个自我增强的网络"，属于愿景方向，刻意不写得太具体——离得越远，越该保持方向而非细节。

**命题**：当注册、调用、分账、结算、声誉都能自动跑起来后，让网络开始自我增强——贡献者越多 → 资产越多 → 调用越多 → 收益越多 → 吸引更多贡献者。

**方向（不排死顺序）**：

- **求职者 → 创作者通路**：让人把自己的经验/技能沉淀成可注册、可被调用、可累积版税的资产。这把"求职"和"创作"两端接成一个循环。
- **贡献者网络规模化**：多方分账从"几个人"长到"一条任务背后一长串署名"。
- **声誉经济**：reputation 真正参与撮合与定价（成功率高/响应快的资产被优先调用、可要更高价）。
- **跨境稳定币结算成为默认**：跨境远程任务天然适合稳定币结算（你的目标用户跨境，这是甜区）。
- **无头任务市场 / MCP 入口**：HireNet 自身成为一个被外部 agent 直接调用的"任务市场无头商户"——核心形态可能是"一个 MCP 服务器 + 一个面向人的展示页"，而不是"一个网站 + 一个 MCP 附件"。

---

## 收尾：怎么记住这条线

把整条路线图压成一句话给自己：

> **Phase 1 证明它能跑；Phase 2 让它可信（记账+身份）；Phase 3 让价值真的流动、网络打开；Phase 4 让网络自己转起来。**

任何时候想插一个新功能，先问一句：**它坐在哪个模型上？那个模型定死了吗？** 没定死，就先别在上面盖楼。
